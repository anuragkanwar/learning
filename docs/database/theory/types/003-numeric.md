# Numeric Types

> PostgreSQL offers integers, arbitrary-precision decimals, floating-point numbers, and auto-incrementing sequences. Choose based on range, precision needs, and storage budget.

## Type Overview

| Type | Storage | Range / Precision | Use Case |
|------|---------|-------------------|----------|
| `SMALLINT` | 2 bytes | -32,768 to 32,767 | Small counters, status codes |
| `INTEGER` | 4 bytes | -2.1B to 2.1B | Primary keys, standard counts |
| `BIGINT` | 8 bytes | -9.22 quintillion to 9.22 quintillion | Large IDs, big counters |
| `SMALLSERIAL` | 2 bytes | 1 to 32,767 | Auto-increment small IDs |
| `SERIAL` | 4 bytes | 1 to 2.1B | Auto-increment standard IDs |
| `BIGSERIAL` | 8 bytes | 1 to 9.22 quintillion | Auto-increment large IDs |
| `NUMERIC(p,s)` | Variable | Up to 131,072 digits | Money, exact calculations |
| `DECIMAL(p,s)` | Variable | Same as NUMERIC | Alias for NUMERIC |
| `REAL` | 4 bytes | 6 decimal digits precision | Approximate values, sensors |
| `DOUBLE PRECISION` | 8 bytes | 15 decimal digits precision | Scientific calculations |

## Integer Types

### SMALLINT

```plsql
CREATE TABLE products (
    id SMALLINT,           -- 2 bytes
    quantity SMALLINT
);

INSERT INTO products VALUES (1, 100);
INSERT INTO products VALUES (40000, 1);  -- ERROR: out of range
```

### INTEGER (INT)

Default choice for most integer columns:

```plsql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,   -- 4 bytes, up to 2.1 billion
    age INTEGER
);
```

### BIGINT

```plsql
CREATE TABLE events (
    id BIGINT PRIMARY KEY,    -- 8 bytes
    event_id BIGINT
);

-- Use when INTEGER range is insufficient
-- Example: high-volume logging, distributed IDs
```

### Integer Overflow

PostgreSQL follows the SQL standard — integer overflow raises an error:

```plsql
SELECT 2147483647 + 1;           -- ERROR: integer out of range
SELECT 2147483647::bigint + 1;   -- 2147483648 (no overflow)
SELECT 32767::smallint + 1;      -- ERROR: smallint out of range
```

## Serial Types — Auto-increment

`SERIAL`, `SMALLSERIAL`, and `BIGSERIAL` are not true types — they are syntactic sugar that creates an integer column + a sequence:

```plsql
CREATE TABLE users (
    id SERIAL PRIMARY KEY
    -- Actually creates:
    -- id INTEGER NOT NULL DEFAULT nextval('users_id_seq')
    -- Also creates sequence: users_id_seq
);

INSERT INTO users DEFAULT VALUES;  -- id = 1
INSERT INTO users DEFAULT VALUES;  -- id = 2
```

Desugared equivalent:

```plsql
CREATE SEQUENCE users_id_seq;

CREATE TABLE users (
    id INTEGER NOT NULL DEFAULT nextval('users_id_seq')
);

ALTER SEQUENCE users_id_seq OWNED BY users.id;
```

### Serial Gap Behavior

Sequences are non-transactional — gaps can appear from:

```plsql
INSERT INTO users DEFAULT VALUES;     -- id = 1 (committed)
INSERT INTO users DEFAULT VALUES;     -- id = 2 (rolled back!)
ROLLBACK;
INSERT INTO users DEFAULT VALUES;     -- id = 3 (gap at 2)
```

- **Rollbacks** — the sequence does not roll back
- **Crashes** — sequence values are not WAL-logged on every increment
- **Caching** — `CREATE SEQUENCE ... CACHE 100` pre-allocates 100 values per session

### IDENTITY (SQL Standard, PostgreSQL 10+)

Prefer `GENERATED AS IDENTITY` over `SERIAL` for new schemas:

```plsql
CREATE TABLE users (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    -- Also: GENERATED BY DEFAULT AS IDENTITY
    username TEXT
);

INSERT INTO users (username) VALUES ('alice');  -- id auto-generated
INSERT INTO users (id, username) VALUES (100, 'bob');  -- ERROR with ALWAYS
INSERT INTO users (id, username) VALUES (100, 'bob');  -- OK with BY DEFAULT
```

| Feature | `SERIAL` | `IDENTITY` |
|---------|----------|------------|
| Standard | PostgreSQL-specific | SQL standard |
| Sequence ownership | Manual or automatic | Automatic |
| Override | Always allowed | `BY DEFAULT` or `ALWAYS` |
| Dependency tracking | Weaker | Stronger |
| Schema migration | Harder | Easier (DROP IDENTITY) |

## NUMERIC / DECIMAL — Exact Precision

Used when exact precision is required — no rounding errors:

```plsql
CREATE TABLE prices (
    product_id INTEGER,
    price NUMERIC(10, 2),       -- 10 digits total, 2 after decimal
    tax_rate NUMERIC(5, 4),     -- max 0.9999
    precise NUMERIC             -- unlimited precision (up to 131072 digits)
);
```

### Declaration

| `NUMERIC(p, s)` | Meaning |
|----------------|---------|
| `p` | Precision — total digits (both sides of decimal) |
| `s` | Scale — digits after decimal |

```plsql
NUMERIC(5, 2)  -- range: -999.99 to 999.99
NUMERIC(10, 4) -- range: -999999.9999 to 999999.9999
NUMERIC        -- no limit (up to 131072 digits), variable storage
```

### Rounding Behavior

PostgreSQL rounds NUMERIC to the declared scale:

```plsql
SELECT 123.456::numeric(5, 2);   -- 123.46 (rounded up)
SELECT 123.454::numeric(5, 2);   -- 123.45 (rounded down)
SELECT 123.455::numeric(5, 2);   -- 123.46 (standard round half-up? let's see)
```

Actually, PostgreSQL rounds to nearest, with ties going to the nearest even number (banker's rounding), but for NUMERIC(p,s) with exact precision, it rounds half away from zero? Let me check.

Actually in PostgreSQL:
- `NUMERIC` rounding follows the `round()` function behavior: half away from zero
- `123.455` → `123.46` (half up)
- `123.465` → `123.47` (half up)

### Storage

NUMERIC storage is variable — depends on precision:

```plsql
-- Storage calculation:
-- 2 bytes overhead + ceil(precision / 2) bytes
NUMERIC(5, 2)   -- ~5 bytes
NUMERIC(20, 5)  -- ~12 bytes
NUMERIC         -- up to ~64KB (131072 digits)
```

## Floating-Point Types

### REAL (FLOAT4) — 4 bytes

```plsql
CREATE TABLE measurements (
    sensor_id INTEGER,
    temperature REAL,          -- ~6 decimal digits precision
    humidity REAL
);

-- Precision example:
SELECT 0.123456789::real;  -- 0.12345679  (rounded to ~6 digits)
```

### DOUBLE PRECISION (FLOAT8) — 8 bytes

```plsql
CREATE TABLE scientific_data (
    id INTEGER,
    value DOUBLE PRECISION   -- ~15 decimal digits precision
);

SELECT 0.1234567890123456789::double precision;  -- 0.1234567890123457
```

### Floating-Point Precision Issues

Floating-point numbers are approximate — never use them for money:

```plsql
SELECT 0.1::real + 0.2::real;           -- 0.30000001 (not 0.3!)
SELECT 0.1::double precision + 0.2::double precision;  -- 0.30000000000000004
SELECT 0.1::numeric + 0.2::numeric;     -- 0.3 (exact)
SELECT 1.0::real / 3.0::real;           -- 0.33333334
```

### Special Floating-Point Values

```plsql
SELECT 'NaN'::real;           -- 'NaN' (Not a Number)
SELECT 'Infinity'::real;      -- Infinity
SELECT '-Infinity'::real;     -- -Infinity

SELECT 'NaN'::real > 100;     -- FALSE (NaN comparisons return FALSE)
SELECT 'NaN'::real = 'NaN'::real;  -- FALSE (NaN != NaN!)
SELECT 'NaN'::real IS NOT DISTINCT FROM 'NaN'::real;  -- TRUE
```

## Choosing the Right Type

### Guideline

| Scenario | Type |
|----------|------|
| Primary key (standard table) | `INTEGER` (or `GENERATED AS IDENTITY`) |
| Primary key (huge table) | `BIGINT` (or `BIGINT GENERATED AS IDENTITY`) |
| Money / currency | `NUMERIC(10, 2)` or `NUMERIC(14, 4)` |
| Scientific calculations | `DOUBLE PRECISION` |
| Sensor data (precision not critical) | `REAL` |
| Small lookup table key | `SMALLINT` |
| Auto-increment (new code) | `GENERATED AS IDENTITY` |
| Auto-increment (legacy) | `SERIAL` |

### Money Type

PostgreSQL has a `MONEY` type but it is locale-dependent and generally discouraged:

```plsql
CREATE TABLE products (
    price MONEY
);

SET lc_monetary = 'en_US.UTF-8';
SELECT price FROM products;  -- '$12.99'

SET lc_monetary = 'de_DE.UTF-8';
SELECT price FROM products;  -- '12,99 EUR'
```

:::tip

Prefer `NUMERIC` for money — it avoids locale surprises and works consistently across clients:

```plsql
CREATE TABLE products (
    price NUMERIC(10, 2) NOT NULL,
    currency_code CHAR(3) NOT NULL DEFAULT 'USD'
);
```
:::

## Arithmetic Behavior

### Division

```plsql
-- Integer division truncates
SELECT 5 / 2;                        -- 2 (integer)

-- Force decimal with NUMERIC
SELECT 5::numeric / 2;               -- 2.5000000000
SELECT 5.0 / 2;                      -- 2.5 (implicit numeric)

-- REAL / DOUBLE division
SELECT 5::real / 2;                  -- 2.5
SELECT 5::double precision / 2;      -- 2.5
```

### Modulo

```plsql
SELECT 7 % 3;              -- 1 (positive)
SELECT -7 % 3;             -- -1 (sign follows dividend)
SELECT 7.5 % 2.5;          -- 0.0 (modulo works with numeric)
```

### Mathematical Functions

```plsql
SELECT ABS(-5);                     -- 5
SELECT CEIL(4.2);                   -- 5
SELECT FLOOR(4.8);                  -- 4
SELECT ROUND(4.5);                  -- 5
SELECT ROUND(4.5, 0);              -- 5 (same)
SELECT ROUND(123.456, 2);          -- 123.46
SELECT TRUNC(123.456, 2);          -- 123.45 (truncate, no rounding)
SELECT POWER(2, 10);               -- 1024
SELECT SQRT(25);                    -- 5
SELECT MOD(7, 3);                   -- 1
SELECT DIV(7, 3);                   -- 2 (integer division)
```

## Casting Between Types

```plsql
-- Integer to numeric
SELECT 5::numeric;                  -- 5
SELECT 5::numeric(10, 2);          -- 5.00

-- Numeric to integer (truncates)
SELECT 5.9::int;                    -- 5 (truncates toward zero!)
SELECT 5.9::integer;               -- 5
SELECT -5.9::int;                  -- -5

-- Round instead of truncate
SELECT ROUND(5.9)::int;            -- 6

-- Float to numeric
SELECT 0.3::double precision::numeric;  -- 0.29999999999999999 (precision artifacts!)
SELECT 0.3::numeric;                -- 0.3 (exact)
```

:::warning

Casting `DOUBLE PRECISION` or `REAL` to `NUMERIC` carries the floating-point approximation with it:

```plsql
SELECT 0.3::double precision::numeric(10, 2);  -- 0.30 (looks correct)
SELECT 0.1 + 0.2;                              -- 0.30000000000000004
SELECT (0.1::double precision + 0.2::double precision)::numeric;
-- 0.30000000000000004 (the floating-point error is preserved)
```
:::

## Performance

| Type | Speed | Notes |
|------|-------|-------|
| `INTEGER` | Fastest | Native CPU word size, most efficient |
| `BIGINT` | Nearly as fast | Slightly larger, still native |
| `SMALLINT` | Slower than INT | CPU prefers 4-byte alignment |
| `NUMERIC` | Significantly slower | Variable-length, software arithmetic |
| `DOUBLE PRECISION` | Fast | Hardware FPU, native |
| `REAL` | Fast | Hardware FPU, native |

```plsql
-- NUMERIC arithmetic is ~5-10x slower than DOUBLE PRECISION
-- Only use NUMERIC when exact precision matters (money, financial)
```

## Gotchas

| # | Gotcha | Detail |
|---|--------|--------|
| 1 | **Floating-point is approximate** | `0.1 + 0.2 != 0.3` — never use REAL/DOUBLE for money |
| 2 | **Integer division truncates** | `5 / 2 = 2`, not 2.5. Cast one operand to numeric |
| 3 | **NUMERIC is slow** | Software arithmetic — avoid in hot paths if precision not needed |
| 4 | **SERIAL gaps are normal** | Rollbacks, crashes, and caching create gaps in sequences |
| 5 | **Cast from float to numeric preserves error** | `0.3::double precision::numeric` is not exactly 0.3 |
| 6 | **OID is deprecated** | `OID` type is 4 bytes but deprecated — use INTEGER or BIGINT |
| 7 | **INTEGER vs INT vs INT4** | All aliases for the same type — no difference |
| 8 | **NUMERIC without precision** | `NUMERIC` with no (p,s) is flexible but slower and uses more storage |
| 9 | **Serial does not guarantee uniqueness** | Only the sequence generates unique values — manual inserts can collide |
| 10 | **SERIAL vs IDENTITY on ALTER TABLE** | Changing a column from SERIAL to IDENTITY requires careful migration |

## Cheat Sheet

```plsql
-- ==================== DECLARATION ====================
col SMALLINT              -- 2 bytes, range ±32K
col INTEGER               -- 4 bytes, range ±2.1B
col BIGINT                -- 8 bytes, range ±9.2 quintillion
col NUMERIC(10, 2)        -- exact, up to 131072 digits
col REAL                  -- 4 bytes, ~6 decimal digits precision
col DOUBLE PRECISION      -- 8 bytes, ~15 decimal digits precision

-- ==================== AUTO-INCREMENT ====================
col SERIAL                          -- INTEGER + sequence (legacy)
col INTEGER GENERATED ALWAYS AS IDENTITY  -- SQL standard (preferred)

-- ==================== CASTING ====================
5::numeric(10, 2)          -- 5.00
5.9::int                   -- 5 (truncates!)
ROUND(5.9)::int            -- 6 (rounds)
'5'::integer               -- string to int
0.1::real + 0.2::real     -- 0.30000001 (not 0.3!)

-- ==================== ARITHMETIC ====================
5 / 2                      -- 2 (integer division)
5.0 / 2                    -- 2.5 (decimal division)
5 % 3                      -- 2 (modulo)
5 ^ 3                      -- 125 (power)
```
